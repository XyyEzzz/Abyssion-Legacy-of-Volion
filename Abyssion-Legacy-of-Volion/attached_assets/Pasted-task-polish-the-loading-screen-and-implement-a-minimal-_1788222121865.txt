--------------------------------------------------
SAVE ARCHITECTURE
--------------------------------------------------

replace the current single-save assumption with exactly 3 local save slots for now.

each slot must contain an independent game-progress state.

per-slot data must preserve the existing gameplay persistence, including:

- player state
- quests
- completed quest ids
- encounter defeats
- npc memory
- inventory/progression data already persisted by the current system
- any other existing gameplay state that is intentionally persisted by the current save system

do not remove existing persisted fields merely because they are not explicitly listed above.

--------------------------------------------------
GLOBAL VS PER-SLOT DATA
--------------------------------------------------

keep global data separate from game-progress data.

settings and HUD configuration should remain global if that matches the current architecture.

do NOT duplicate global settings/HUD data into every save slot unless the existing architecture requires it.

the important distinction is:

global configuration
≠
individual game progress

--------------------------------------------------
ACTIVE SLOT
--------------------------------------------------

the currently selected save slot must be explicit.

requirements:

- track the active slot separately from the save data itself.
- normal save operations must always write to the active slot.
- continue must load the selected slot.
- returnToMenu must save the active slot.
- starting a new game must assign the newly created game to the selected slot.
- active-slot information must remain consistent after application reload.
- do not rely solely on transient Zustand memory to determine the active slot.

--------------------------------------------------
SAVE SLOT DISCOVERY
--------------------------------------------------

do NOT use a manually maintained boolean as the source of truth for whether a save exists.

the save-slot state itself must determine whether Continue is available.

avoid repeating the previous single-save problem where:

save data exists
but
hasSaveData says false

the UI must derive slot availability from actual persisted slot data.

--------------------------------------------------
CONTINUE FLOW
--------------------------------------------------

desired flow:

main menu
    ↓
continue
    ↓
save slot selection
    ↓
select occupied slot
    ↓
load that exact slot
    ↓
gameplay

requirements:

- Continue must not load an arbitrary slot.
- occupied slots must be distinguishable from empty slots.
- empty slots cannot accidentally load another save.
- selecting slot 1 must load only slot 1.
- selecting slot 2 must load only slot 2.
- selecting slot 3 must load only slot 3.
- if no slots contain valid saves, Continue should remain unavailable.

--------------------------------------------------
NEW GAME FLOW
--------------------------------------------------

desired flow:

main menu
    ↓
new game
    ↓
save slot selection
    ↓
select empty slot
    ↓
create fresh game
    ↓
gameplay

requirements:

- New Game must create a fresh state.
- New Game must never silently overwrite an occupied slot.
- occupied slots must be protected.
- if all 3 slots are occupied, do not silently replace any slot.
- do not add automatic deletion.
- do not add automatic replacement.
- do not add a confirmation flow for deletion because deletion is not being implemented.

--------------------------------------------------
SAVE BEHAVIOR
--------------------------------------------------

save operations must:

- write only to the active slot.
- preserve all existing persisted gameplay fields.
- update minimal metadata such as last saved timestamp.
- optionally store player level if it is already available.
- never modify other slots.
- never reset another slot.
- never accidentally merge two slots together.

example:

save(slot 1)
→ slot 1 changes
→ slot 2 unchanged
→ slot 3 unchanged

--------------------------------------------------
CORRUPTED / INVALID SAVE
--------------------------------------------------

a corrupted slot must not destroy other slots.

requirements:

- validate persisted slot data before loading.
- invalid slot data should fail safely.
- Continue must not crash because one slot is malformed.
- do not silently overwrite corrupted slots with a new game.
- do not destroy unrelated valid slots.

--------------------------------------------------
LEGACY MIGRATION
--------------------------------------------------

the current project may contain the old single-save format.

inspect the actual legacy format first.

if a valid legacy save exists:

- migrate it into the first available save slot.
- preserve all existing persisted fields.
- do not overwrite an already occupied valid slot.
- write the migrated slot successfully before removing/retiring the legacy representation.
- migration must be deterministic.
- migration must be safe if interrupted or repeated.
- if no valid legacy save exists, do nothing.

do NOT simply delete the old `abyssion_save` key before migration succeeds.
